# MMoE：多门控混合专家模型

## 1. 概述

&emsp;MMoE（Multi-gate Mixture-of-Experts，**多门控混合专家**）是 Google 2018 年发表于 KDD 的多任务学习模型，核心思想一句话：**准备一组"专家"网络，给每个任务配一个独立的"门控"网络，门控对专家输出做加权求和，让不同任务自适应地选择最合适的专家组合。**

&emsp;为什么重要？推荐系统几乎没有单目标的——同时要预估点击率（CTR）、转化率（CVR）、完播时长、点赞、收藏……最简单的主流做法是 Shared-Bottom（共享底层 + 多任务塔），但任务相关性弱时会出现**跷跷板现象**：一个任务指标涨了，另一个任务就跌。MMoE 用"多门控 + 专家分化"同时保住参数共享（缓解稀疏）和任务专属表示（缓解冲突），成为工业界最常用的多任务基础结构之一，也是面试高频考点。

## 2. 背景：多任务学习与任务冲突

&emsp;先想清楚一个问题：**为什么不用 K 个独立的单任务模型？** 三个理由：

1. **数据共享**：CVR 等任务正样本稀疏，借用 CTR 任务的海量样本学到的表示，能显著缓解稀疏；
2. **表示复用**：用户/物品特征的表征可以跨任务复用，避免重复训练 K 套 embedding；
3. **线上成本**：一个模型一次前向输出 K 个分数，比 K 个模型便宜得多。

&emsp;于是最自然的结构出现了——**Shared-Bottom**：所有任务共享一个底层网络（通常是 embedding + MLP），再各自接一个任务塔（tower）输出。它的共享是**硬共享**（hard parameter sharing）：底层参数被所有任务的梯度共同更新。

&emsp;硬共享的问题在于：**不同任务的最优表示方向可能不一致甚至冲突**。举例：视频推荐中"点击率"任务喜欢"标题党、封面吸引人"的特征方向，而"完播时长"任务喜欢"内容质量高"的方向——同一个共享表示被两个方向的梯度同时拉扯，只能折中。结果就是**跷跷板现象（Seesaw Phenomenon）**：优化任务 A 时任务 B 变差，反之亦然。直觉类比：两个人共用一把椅子，一个想往左挪、一个想往右挪，椅子只能停在中间，两个人都坐不舒服。

&emsp;核心矛盾浮出水面：**完全共享**（Shared-Bottom）参数省、缓解稀疏，但任务冲突时互相拖累；**完全独立**（K 个模型）没有冲突，但放弃共享收益。MMoE 的目标就是在这两者之间找一个"软"的平衡点。

## 3. 核心原理：门控混合专家

&emsp;先讲大白话。MMoE 把"共享底层"拆成两部分：

- **专家（Expert）**：$n$ 个并行的子网络 $f_1, \dots, f_n$，相当于 $n$ 个"各有所长"的共享底座。它们之间参数不共享，但**所有任务共用这一组专家**；
- **门控（Gate）**：每个任务一个门控 $g^k$，输入样本 $x$，输出 $n$ 个权重（softmax 归一化，和为 1），决定"这个样本、这个任务，应该各用多少比例的每个专家"。

&emsp;任务 $k$ 最终拿到的表示，是专家输出的**加权求和**（凸组合）：

$$f^k(x) = \sum_{i=1}^{n} g_i^k(x) \cdot f_i(x)$$

&emsp;严谨定义（设输入 $x \in \mathbb{R}^d$，专家输出维度为 $d'$，共 $K$ 个任务）：

1. 专家网络：$f_i: \mathbb{R}^d \to \mathbb{R}^{d'}$，$i = 1, \dots, n$，通常每个专家是一个多层感知机（MLP）；
2. 任务 $k$ 的门控网络：$g^k(x) = \text{softmax}(W_{gk}\, x)$，其中 $W_{gk} \in \mathbb{R}^{n \times d}$ 是门控权重矩阵，输出 $g^k(x) \in \mathbb{R}^n$，满足 $\sum_{i=1}^{n} g_i^k(x) = 1$ 且 $g_i^k(x) \ge 0$；
3. 任务 $k$ 的塔输入（门控加权组合）：$f^k(x) = \sum_{i=1}^{n} g_i^k(x) \, f_i(x) \in \mathbb{R}^{d'}$；
4. 任务 $k$ 的最终输出：$\hat{y}_k = h_k\big(f^k(x)\big)$，其中 $h_k$ 是任务专属塔（MLP + 输出层）。

&emsp;把核心公式框起来：

$$\boxed{\,f^k(x) = \sum_{i=1}^{n} g_i^k(x)\, f_i(x), \qquad g^k(x) = \text{softmax}(W_{gk}\, x)\,}$$

&emsp;两个直觉要点：

- **"多门控"的含义**：每个任务有自己独立的门控权重 $W_{gk}$，因此任务 A 和任务 B 对同一组专家可以给出完全不同的加权方式——这是 MMoE 与"所有任务共用一个门控"（OMoE）的本质区别；
- **软路由而非硬路由**：门控是 softmax 的稠密权重（每个专家都参与，只是比例不同），全程可微，端到端训练，不需要像稀疏 MoE 那样做不可微的 top-k 选择。

## 4. 模型结构与损失函数

&emsp;整体结构分四层（以 2 任务为例）：

1. **输入层**：特征 $x$（连续特征或 embedding 池化结果）；
2. **专家层**：$n$ 个并列 MLP 专家，输入都是 $x$，输出都是 $d'$ 维（**所有任务共享这一层**）；
3. **门控层**：$K$ 个并列门控（每个任务一个），输入 $x$，softmax 输出 $n$ 维权重；每个任务的塔输入由对应门控对专家输出加权求和得到；
4. **任务塔层**：$K$ 个任务塔，各自输出 $\hat{y}_k$（CTR 塔输出 pCTR、CVR 塔输出 pCVR……）。

&emsp;损失函数是各任务损失的加权和：

$$L = \sum_{k=1}^{K} w_k \, L_k$$

&emsp;其中 $w_k$ 是任务权重（如 CTR 任务和 CVR 任务可设不同权重），$L_k$ 是任务 $k$ 的损失（分类用交叉熵、回归用 MSE）。梯度如何分配？对专家 $i$ 求导，由链式法则：

$$\frac{\partial L_k}{\partial f_i} = g_i^k(x) \cdot \frac{\partial L_k}{\partial f^k}$$

&emsp;注意一个关键事实：**门控值 $g_i^k(x)$ 就是任务 $k$ 对专家 $i$ 的梯度缩放因子**。任务 $k$ 的损失主要"推"那些门控权重大的专家——这为"专家分化"提供了机制保证（见例 2）。

## 5. 为什么 MMoE 有效

1. **软共享缓解任务冲突**：每个任务的塔输入是门控加权后的"任务专属表示"，梯度按门控分流到不同专家，不会像 Shared-Bottom 那样在同一组参数上直接抵消/拉扯（见例 2 的数值演示）。
2. **仍保留共享收益**：所有任务共用同一组专家，专家可同时服务多个任务，稀疏任务（如 CVR）依然能借力；参数总量远小于 K 个独立模型。
3. **门控是自适应的**：门控输入是样本 $x$，所以同一个任务在不同样本上也可以选择不同的专家组合（比如"新用户"样本和"老用户"样本可能偏好不同专家），比固定的任务专属塔更灵活。
4. **专家自动分化**：训练中专家会自发分化——有的专家偏向任务 A，有的偏向任务 B，有的成为"公共专家"服务所有任务，无需人工指定分工。
5. **退化有界**：若专家数 $n=1$ 或门控退化为常数，MMoE 就退化为 Shared-Bottom。这说明 MMoE 是 Shared-Bottom 的严格推广，理论上不会比它差，实践中也几乎总是更好或持平。

## 6. 与其他概念的关系

| 对比对象 | 差异点 |
|---|---|
| Shared-Bottom（硬共享） | 所有任务共用一套底层参数，任务冲突时互相拉扯（跷跷板）；MMoE 用门控实现"软共享"，是它的推广 |
| OMoE（单门控 MoE） | 所有任务共用一个门控，无法为任务定制专家组合，任务间仍有强耦合；MMoE 每个任务一个门控，论文实验显示任务相关性弱时显著优于 OMoE |
| 稀疏 MoE（Shazeer 2017） | 面向大规模模型的条件计算，top-k 稀疏路由省算力；MMoE 是稠密 softmax 门控（全部专家参与），目的是建模任务关系而非省算力 |
| PLE（渐进分层提取） | MMoE 的改进：显式区分"任务专属专家 + 共享专家"，并多层渐进提取，缓解 MMoE 中所有任务竞争专家导致的跷跷板残留 |
| ESMM | ESMM 解决"样本空间偏差 + 数据稀疏"，输出层有 $pCTCVR = pCTR \times pCVR$ 乘法结构先验；MMoE 解决"任务冲突"，作用在表示层。两者互补，可结合：MMoE/PLE 作共享层 + 乘法分解输出 |
| 单任务模型 × K | 无共享收益：数据稀疏、训练/推理成本高；MMoE 用共享专家 + 专属门控在两者间折中 |

## 7. 具体例子

### 例 1：前向计算——同一批专家，两个任务拿到不同表示

**问题**：设 2 个专家、2 个任务（任务 A = CTR，任务 B = CVR）。给定样本 $x$，专家输出 $f_1(x) = (1, 3)$、$f_2(x) = (4, 2)$（2 维）；门控 logits 经 softmax 后，任务 A 的门控 $g^A = (0.7, 0.3)$，任务 B 的门控 $g^B = (0.2, 0.8)$。分别计算两个任务的塔输入 $f^A$、$f^B$。

**步骤**：套用加权求和公式 $f^k = g_1^k f_1 + g_2^k f_2$，逐分量计算。

**计算**：

- 任务 A：$f^A = 0.7 \times (1, 3) + 0.3 \times (4, 2) = (0.7 + 1.2,\; 2.1 + 0.6) = (1.9, 2.7)$
- 任务 B：$f^B = 0.2 \times (1, 3) + 0.8 \times (4, 2) = (0.2 + 3.2,\; 0.6 + 1.6) = (3.4, 2.2)$

**结果解读**：两个任务输入的是**同一组专家**（参数共享），但门控加权后拿到的是**不同的表示**：$f^A = (1.9, 2.7)$ 更接近专家 1 的输出 $(1, 3)$（第一分量占比高），$f^B = (3.4, 2.2)$ 更接近专家 2 的输出 $(4, 2)$。这就是"共享参数、专属表示"——CTR 塔和 CVR 塔可以基于不同的特征方向做决策，互不拖累。

### 例 2：梯度分配——门控如何缓冲任务冲突

**问题**：接例 1 的场景。假设任务 A 塔回传的梯度 $\partial L_A / \partial f^A = (+1, -1)$，任务 B 塔回传的梯度 $\partial L_B / \partial f^B = (-1, +1)$——两个任务的梯度方向**正好相反**（典型冲突）。分别计算 Shared-Bottom 和 MMoE 中共享层的梯度。

**步骤**：Shared-Bottom 的共享层直接接收两任务梯度之和；MMoE 中专家 $i$ 的梯度按门控加权累加：$\dfrac{\partial L}{\partial f_i} = \sum_k g_i^k \, \dfrac{\partial L_k}{\partial f^k}$。

**计算**：

- Shared-Bottom（设共享表示为 $s$）：$\dfrac{\partial L}{\partial s} = (+1, -1) + (-1, +1) = (0, 0)$——**梯度完全抵消**，共享层收不到任何有效信号，两个任务都无法优化；
- MMoE，专家 1（$g^A_1 = 0.7$，$g^B_1 = 0.2$）：$0.7 \times (+1, -1) + 0.2 \times (-1, +1) = (0.5, -0.5)$；
- MMoE，专家 2（$g^A_2 = 0.3$，$g^B_2 = 0.8$）：$0.3 \times (+1, -1) + 0.8 \times (-1, +1) = (-0.5, +0.5)$。

**结果解读**：Shared-Bottom 中反向梯度在共享参数上抵消，这是跷跷板现象在梯度层面的根源；MMoE 中每个专家的净梯度都不为零，且**方向不同**——专家 1 朝任务 A 需要的方向优化、专家 2 朝任务 B 的方向优化，专家自然分化。同时注意：任务 A 塔的输入 $f^A$ 的梯度只由 $L_A$ 决定（$\partial L_A / \partial f^A$），任务 B 的梯度经门控分流后不会直接污染任务 A 的表示。

### 例 3：门控的"软→硬"演化——专家分化是怎么发生的

**问题**：softmax 门控的 logits 尺度不同，加权行为有何差异？设门控对两个专家输出的 logits 分别为 $(0.5, 1.0)$ 与 $(5, 10)$，分别计算 softmax 权重。

**步骤**：套用 $\text{softmax}(z)_i = \dfrac{e^{z_i}}{\sum_j e^{z_j}}$。

**计算**：

- logits $(0.5, 1.0)$：$e^{0.5} \approx 1.649$，$e^{1.0} \approx 2.718$，权重 $= \left(\dfrac{1.649}{4.367},\ \dfrac{2.718}{4.367}\right) \approx (0.38, 0.62)$——接近均匀；
- logits $(5, 10)$：$e^{5} \approx 148.4$，$e^{10} \approx 22026$，权重 $\approx (0.007, 0.993)$——接近 one-hot 硬选择。

**结果解读**：训练早期门控权重小，各专家"雨露均沾"（软路由，类似 $(0.38, 0.62)$）；随着训练推进，门控权重被放大，softmax 趋于硬选择（类似 $(0.007, 0.993)$），**专家被"指派"给了更需要的任务**。这解释了 MMoE 的隐式分工机制：不需要人工指定"专家 1 管 CTR、专家 2 管 CVR"，梯度 + softmax 会在训练中自动完成分化。实践中可以通过统计训练后门控权重的分布（是否分化、熵大小）来诊断模型是否学好了。

## 8. 示例代码（PyTorch）

&emsp;MMoE 的核心实现（2 任务 + 4 专家，仅模型与损失，可直接拼接到自己的数据管线）：

```python
class MMoE(nn.Module):
    def __init__(self, n_in=16, n_experts=4, expert_dim=8, hidden=64):
        super().__init__()
        self.experts = nn.ModuleList([                       # 专家层：所有任务共享
            nn.Sequential(nn.Linear(n_in, expert_dim), nn.ReLU())  # (n, 16) -> (n, 8)
            for _ in range(n_experts)])
        self.gates = nn.ModuleList([                         # 门控层：每个任务一个
            nn.Linear(n_in, n_experts)                       # (n, 16) -> (n, 4)  logits
            for _ in range(2)])
        self.towers = nn.ModuleList([                        # 任务塔层：每个任务一个
            nn.Sequential(nn.Linear(expert_dim, hidden), nn.ReLU(),
                          nn.Linear(hidden, 1))              # (n, 8) -> (n, 1)  logits
            for _ in range(2)])

    def forward(self, x):
        # x: (n, 16)；专家输出堆叠 -> (n, n_experts, expert_dim) = (n, 4, 8)
        e = torch.stack([f(x) for f in self.experts], dim=1)
        outs = []
        for k, (gate, tower) in enumerate(zip(self.gates, self.towers)):
            g = torch.softmax(gate(x), dim=-1)               # (n, 4) 门控权重，和为 1
            fk = torch.einsum("nk,nkd->nd", g, e)            # (n, 8) 任务 k 的加权专家表示
            outs.append(tower(fk).squeeze(-1))               # (n,) 任务 k 输出 logits
        return outs                                          # [logitA, logitB]

# 训练：L = wA * L_A + wB * L_B（两任务等权为例），门控与专家端到端一起训练
logitA, logitB = model(x)                                   # x: (n, 16)，返回 (n,) 的 logits
loss = bce(logitA, yA) + bce(logitB, yB)                    # 交叉熵之和（标量）
loss.backward()                                             # 梯度经门控分流到各专家
```

&emsp;要点：① 专家和门控输入都是 $x$，输出 logits 用 `BCEWithLogitsLoss`；② 门控的 softmax 保证权重和为 1（凸组合）；③ `torch.einsum("nk,nkd->nd", g, e)` 即 $f^k = \sum_i g_i^k f_i$；④ 若要任务权重不等，将两交叉熵乘上 $w_k$ 再相加即可。

## 9. 常见面试问题

**Q1：什么是多任务学习？推荐系统为什么需要它？**

答：多任务学习（MTL）是用一个模型同时学习多个相关任务、共享底层表示的方法。推荐系统需要同时预估 CTR、CVR、时长、点赞等多个目标，MTL 的好处：① 数据共享，稀疏任务（如 CVR 正样本少）借力充足任务（CTR）的表示；② 特征表示跨任务复用，避免重复训练；③ 一次前向输出多个分数，节省线上资源。

**Q2：Shared-Bottom 有什么问题？什么是跷跷板现象？**

答：Shared-Bottom 所有任务共享底层参数，是硬共享。任务相关性弱时，不同任务的最优表示方向不一致甚至冲突，共享参数被多个方向的梯度拉扯，只能折中——优化一个任务时另一个任务变差，此消彼长，称为跷跷板现象（Seesaw Phenomenon）。典型例子：视频推荐的"点击率"（偏好标题党特征）与"完播时长"（偏好内容质量特征）互相冲突。

**Q3：写出 MMoE 的前向公式，并解释每个符号。**

答：设输入 $x$，共 $n$ 个专家 $f_1,\dots,f_n$，$K$ 个任务。专家输出 $f_i(x)$；任务 $k$ 的门控 $g^k(x) = \text{softmax}(W_{gk}x)$（$W_{gk}$ 是 $n \times d$ 权重矩阵，输出 $n$ 维非负权重且和为 1）；任务 $k$ 的塔输入 $f^k(x) = \sum_{i=1}^{n} g_i^k(x) f_i(x)$；最终输出 $\hat{y}_k = h_k(f^k(x))$，$h_k$ 是任务塔。核心：每个任务有独立门控，对同一组专家做不同加权。

**Q4：MMoE 如何缓解任务冲突？梯度是怎么分配的？**

答：每个任务的塔输入是"门控加权后的专属表示"，梯度经门控分流：$\partial L_k / \partial f_i = g_i^k(x) \cdot \partial L_k / \partial f^k$，门控值即梯度缩放因子。冲突的梯度（如例 2 中 $(+1,-1)$ 与 $(-1,+1)$）被不同门控按比例分给不同专家，避免在共享参数上直接抵消；专家在训练中分化成任务专属角色，从而缓解跷跷板。

**Q5：MMoE 和 OMoE（单门控 MoE）有什么区别？**

答：OMoE 所有任务共用一个门控，意味着所有任务对专家的加权方式完全相同，任务间耦合依然很强；MMoE 每个任务一个门控（"多门控"），可以学到不同的专家组合。论文实验表明，任务相关性越弱，MMoE 相对 OMoE 的优势越明显。

**Q6：MMoE 和稀疏 MoE（如 Shazeer 2017）有什么区别？**

答：稀疏 MoE 面向大规模模型，用 top-k 稀疏路由做条件计算、省算力，路由选择不可微；MMoE 面向多任务建模，门控是稠密 softmax（所有专家都参与，可微），目标是让任务自适应组合专家以缓解冲突，而非省计算。二者名字相似但动机不同。

**Q7：MMoE 有哪些局限性？专家数量怎么选？**

答：局限：① 所有专家被所有任务共享，任务强冲突时专家竞争依然存在跷跷板残留（PLE 论文指出）；② 参数量随专家数线性增长，训练和推理开销变大；③ 门控可能陷入局部最优或退化。专家数一般取 4~8 个（视任务数与数据量），实践中观察门控权重是否分化、AUC 是否有增益来调整；也可以对比门控均匀/退化的诊断结果。

**Q8：MMoE 和 ESMM 是什么关系？能结合吗？**

答：两者解决不同问题：MMoE 在表示层解决任务冲突；ESMM 在输出层利用"转化依赖点击"的漏斗先验（$pCTCVR = pCTR \times pCVR$），解决 CVR 的样本选择偏差与数据稀疏。可以结合，工业界常见做法：用 MMoE（或 PLE）替换 ESMM 的共享 embedding + 双塔作为表示层，再保留乘法分解输出，兼顾任务冲突与样本空间问题。

**Q9：PLE 是如何改进 MMoE 的？为什么 MMoE 仍有跷跷板？**

答：MMoE 中所有专家被所有任务共享，任务强冲突时它们会"竞争"专家，跷跷板现象并未完全消除。PLE（Progressive Layered Extraction）把专家显式分为任务专属专家和共享专家两组，任务塔输入 = 专属专家 + 共享专家的加权组合（CGC 是其单层版本），并多层渐进提取、每层输出作为上层输入，让任务既有私有容量又有共享容量，进一步缓解跷跷板。

**Q10：如何诊断 MMoE 是否训练好了？门控退化怎么办？（进阶）**

答：训练后统计各任务门控权重的分布：若某任务门控接近均匀（熵大），说明该任务没有分化出专属专家、专家冗余；若接近 one-hot，说明专家已专属化，符合预期；多个任务的门控高度相似则说明任务关系强、MMoE 的优势没发挥出来。门控退化（如始终均匀）时可尝试：加大训练轮数、调整门控初始化、对门控加温度或熵正则；若冲突实在严重，直接换 PLE 显式分离专属/共享专家。
