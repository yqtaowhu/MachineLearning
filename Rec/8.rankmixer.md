# RankMixer：工业级推荐排序模型的 Scaling 之路

## 1. 概述

**RankMixer** 是字节跳动 2025 年提出的推荐排序（Ranking）模型架构（论文 *RankMixer: Scaling Up Ranking Models in Industrial Recommenders*，arXiv:2507.15551），核心思想是：**用一套"硬件感知（hardware-aware）"的统一架构，替换掉 CPU 时代遗留的各种手工特征交叉模块，让推荐排序模型也能像 LLM 一样享受 Scaling Law 的红利**。

> 一句话：**把推荐特征当成 token，用"无参数的 Token Mixing + 参数隔离的 Per-token FFN"替代自注意力和杂牌交叉模块，参数量放大 100 倍而延迟不变。**

**为什么重要：**

1. **打破了"推荐模型堆不动"的困境**：传统 DLRM 的稠密部分堆参数收益很快饱和；RankMixer 在抖音万亿级样本上验证了参数量与 AUC 之间的陡峭幂律曲线。
2. **MFU 提升 10 倍**：把模型 FLOPs 利用率（Model FLOPs Utilization）从 4.5% 提到 45%，让模型从"内存受限（memory-bound）"变成"计算受限（compute-bound）"，这才是 GPU 该有的样子。
3. **真实业务收益巨大**：已在抖音 Feed 推荐全量部署，1B 稠密参数下用户活跃天数 +0.3%、App 总时长 +1.08%、点赞 +2.39%；广告场景 AUC +0.73%、广告主价值 +3.9%。
4. **开创了"判别式 Scaling"路线**：与快手 OneRec 的生成式路线并行，证明了不换范式、只改造判别式排序主干同样能 Scale，后续影响了 TokenMixer-Large、OneTrans、UniMixer 等一系列工作。

**两个关键背景问题**（理解了它们就理解了这篇论文的动机）：

- 工业推荐有严格的延迟约束（几十毫秒）和极高 QPS，不能像 LLM 那样无脑加参数；
- 传统排序模型里 DCN、DHEN 等手工交叉模块是为 CPU 设计的，算子碎、访存多，在 GPU 上 MFU 只有个位数——**算力都浪费在等数据上了**。

## 2. 核心原理

### 2.1 整体架构

**直觉**：RankMixer 长得像一个"为推荐特化的 Transformer"——同样是 $L$ 层 Block 堆叠、同样有残差和 LayerNorm，但把两个最贵的部件都换掉了：自注意力换成免费的 Token Mixing，共享 FFN 换成每 token 独立的 Per-token FFN。

每个 RankMixer Block 的计算为：

$$\mathbf{S}_{n-1} = \mathrm{LN}\left(\mathrm{TokenMixing}(\mathbf{X}_{n-1}) + \mathbf{X}_{n-1}\right)$$

$$\mathbf{X}_{n} = \mathrm{LN}\left(\mathrm{PFFN}(\mathbf{S}_{n-1}) + \mathbf{S}_{n-1}\right)$$

逐符号解释：

- $\mathbf{X}_n \in \mathbb{R}^{T \times D}$：第 $n$ 层 Block 的输出，由 $T$ 个 token 组成，每个 token 是 $D$ 维向量
- $T$：token 数量（由特征分组决定，100M 版 $T=16$，1B 版 $T=32$）
- $D$：模型隐藏维度（100M 版 768，1B 版 1536）
- $\mathrm{LN}(\cdot)$：LayerNorm；两个子层都带残差连接
- $\mathrm{TokenMixing}(\cdot)$：跨 token 的信息交换（无参数）
- $\mathrm{PFFN}(\cdot)$：Per-token FFN，每个 token 有自己独立的一套 FFN 参数

最后一层输出 $\mathbf{X}_L$ 做 **mean pooling** 得到 $\mathbf{o}_{\text{output}}$，接多任务预测头（完播、点赞、评论等）。

### 2.2 特征 Tokenization：把异构特征切成 token

**直觉**：LLM 的 token 是词，天然同质；推荐的特征却五花八门（用户 ID、视频 ID、行为序列、交叉统计量……）。RankMixer 的做法是：**按语义把几百个特征分成若干组，每组拼成一段向量，再切出固定维度的 token**——让每个 token 代表一个"语义连贯"的特征子空间。

所有特征先转成 embedding 并拼接：

$$e_{\text{input}} = [e_1; e_2; \dots; e_N]$$

然后按固定长度切分并投影：

$$\mathbf{x}_i = \mathrm{Proj}\left(e_{\text{input}}[d \cdot (i-1) : d \cdot i]\right), \quad i = 1, \dots, T$$

- $N$：特征组数量；$d$：每个 token 切分前的固定维度
- $\mathrm{Proj}$：线性投影，把切出来的片段映射到统一的 $D$ 维
- 用户行为序列特征先经过序列模块（如 LONGER）编码，再作为一个语义组进入 tokenization

这一步的意义：**token 边界对齐了语义边界**，后面 Per-token FFN 的"参数隔离"才有明确的语义含义（比如某个 FFN 专门处理"用户画像"子空间）。

### 2.3 Multi-head Token Mixing：无参数的全局信息交换

**直觉**：这是一个"洗牌"操作——把每个 token 切成 $H$ 份（head），然后**所有 token 的第 $h$ 份拼成一个新 token**。洗牌后每个新 token 都含有全部原 token 的信息片段，从而实现跨特征的全局交互。

具体分两步。第一步，把每个 token $\mathbf{x}_t$ 均匀切成 $H$ 个 head：

$$\left[\mathbf{x}_t^{(1)} \| \mathbf{x}_t^{(2)} \| \dots \| \mathbf{x}_t^{(H)}\right] = \mathrm{SplitHead}(\mathbf{x}_t)$$

第二步，把所有 token 的同一个 head 拼接成新 token：

$$\mathbf{s}^h = \mathrm{Concat}\left(\mathbf{x}_1^h, \mathbf{x}_2^h, \dots, \mathbf{x}_T^h\right)$$

论文取 $H = T$，保证混合前后 token 数不变（这样才能做残差连接）。混合后同样接残差 + LN：

$$\mathbf{s}_1, \dots, \mathbf{s}_T = \mathrm{LN}\left(\mathrm{TokenMixing}(\mathbf{x}_1, \dots, \mathbf{x}_T) + (\mathbf{x}_1, \dots, \mathbf{x}_T)\right)$$

**为什么不用自注意力？** 这是本文最有洞察力的论点之一：

1. 自注意力用 token 内积算相似度，前提是**所有 token 共享同一个语义空间**（NLP 里都是词向量，成立）；
2. 推荐里 token 来自异构语义空间（"用户 ID 子空间"和"视频统计量子空间"做内积没有意义），且 ID 空间可能有几亿元素；
3. 实验证明：自注意力在这里**不仅不涨点，还更贵**——消融实验中用 Self-Attention 替换 Token Mixing，AUC 反而 $-0.03\%$，参数 $+16\%$，FLOPs $+71.8\%$。

### 2.4 Per-token FFN：参数隔离的特征子空间建模

**直觉**：Transformer 里所有 token 共享一套 FFN；RankMixer 反过来，**每个 token 用自己专属的 FFN**。这样"用户画像 token"和"视频内容 token"各学各的变换，互不干扰。

对第 $t$ 个 token $\mathbf{s}_t$：

$$\mathbf{v}_t = f_{\text{pffn}}^{t,2}\left(\mathrm{GELU}\left(f_{\text{pffn}}^{t,1}(\mathbf{s}_t)\right)\right), \qquad f_{\text{pffn}}^{t,i}(\mathbf{x}) = \mathbf{x}\mathbf{W}_{\text{pffn}}^{t,i} + \mathbf{b}_{\text{pffn}}^{t,i}$$

- $\mathbf{W}_{\text{pffn}}^{t,1} \in \mathbb{R}^{D \times kD}$，$\mathbf{W}_{\text{pffn}}^{t,2} \in \mathbb{R}^{kD \times D}$：第 $t$ 个 token **专属**的两层权重，$k$ 是隐层放大系数
- 关键点：**参数量变成共享 FFN 的 $T$ 倍，但单个 token 的计算量完全不变**——参数与 FLOPs 解耦，这是 Scaling 的核心杠杆

**为什么不用共享 FFN？** 传统 DLRM/DHEN 把所有特征混进一个交叉模块，高频特征域（如热门 item ID）会淹没长尾信号。参数隔离让每个子空间有独立容量。消融显示：Per-token FFN 退化为共享 FFN，AUC 掉 $-0.31\%$。

**与 MMoE / Transformer 的本质区别**：

- MMoE：多个 expert 吃**同一个输入**，参数不同；
- Transformer：不同输入吃**同一套 FFN**，参数共享；
- RankMixer：**输入和参数同时切分**——每个 Per-token FFN 看的是不同的 token，天然多样性。

### 2.5 Sparse MoE 变体：ReLU 路由 + DTSI

**直觉**：想把模型从 1B 扩到 10B，稠密 FFN 的计算量扛不住，于是把每个 token 的 FFN 换成一堆 expert（Sparse MoE）——容量涨、计算基本不变。但直接套用 LLM 的 Top-k MoE 会翻车，原因有二：

1. **均匀 Top-k 不合理**：所有 token 一律激活 $k$ 个 expert，信息量大的 token 吃不饱，信息量小的 token 浪费预算；
2. **expert 训练不足**：Per-token FFN 已经把参数乘了 $T$ 倍，再叠 expert 会让 expert 总数爆炸，路由不均导致大量"死 expert"。

**解法一：ReLU 路由**（替代 Top-k + softmax）。对 token $\mathbf{s}_i$ 和第 $j$ 个 expert $e_{i,j}$：

$$G_{i,j} = \mathrm{ReLU}\left(h(\mathbf{s}_i)\right), \qquad \mathbf{v}_i = \sum_{j=1}^{N_e} G_{i,j} \, e_{i,j}(\mathbf{s}_i)$$

- $h(\cdot)$：路由器（router）；$G_{i,j}$：expert 的门控权重
- $\mathrm{ReLU}$ 输出天然稀疏（负值即不激活），且**每个 token 激活的 expert 数量是动态的**——信息量大的 token 自动激活更多 expert
- 稀疏度靠 $\ell_1$ 正则控制，把平均激活率压在预算附近：

$$\mathcal{L} = \mathcal{L}_{\text{task}} + \lambda \, \mathcal{L}_{\mathrm{reg}}, \qquad \mathcal{L}_{\mathrm{reg}} = \sum_{i=1}^{N_t} \sum_{j=1}^{N_e} G_{i,j}$$

**解法二：DTSI-MoE（Dense-Training / Sparse-Inference）**。设两个路由器 $h_{\text{train}}$ 和 $h_{\text{infer}}$，$\mathcal{L}_{\mathrm{reg}}$ **只作用于** $h_{\text{infer}}$。训练时两个路由器都更新（训练路径接近稠密激活，所有 expert 都能拿到充足梯度），推理时只用稀疏的 $h_{\text{infer}}$ 省成本。

效果：激活率压到 $1/8$ 时，DTSI + ReLU 路由几乎无损保留 1B 稠密模型的 AUC，容量扩大 8 倍以上，吞吐提升 50%+；而 Vanilla SMoE 的 AUC 随稀疏度增加单调下滑。

### 2.6 Scaling 方向与延迟分解公式

稠密版 RankMixer 单样本的参数量与 FLOPs：

$$\#\text{Param} \approx 2kLTD^2, \qquad \text{FLOPs} \approx 4kLTD^2$$

可沿四个正交方向放大：token 数 $T$、宽度 $D$、层数 $L$、expert 数 $E$（MoE 版）。论文实验发现与 LLM 一致的结论：**效果主要由总参数量决定，往哪个方向堆几乎等价**；但从算力效率看，加宽 $D$ 能得到更大的矩阵乘 shape、MFU 更高，所以最终 100M 配置为 $(D{=}768, T{=}16, L{=}2)$，1B 配置为 $(D{=}1536, T{=}32, L{=}2)$——都只有 2 层，宽度优先。

线上延迟可分解为：

$$\text{Latency} = \frac{\#\text{Param} \times (\text{FLOPs/Param})}{\text{MFU} \times \text{Theoretical Hardware FLOPs}}$$

这个公式是全文工程哲学的浓缩：**参数涨 70 倍不可怕，只要分母（MFU × 硬件算力）和 FLOPs/Param 比同步优化，延迟就能压住**（详见例子 3）。

## 3. 重要性质与设计动机

### 3.1 参数增长与 FLOPs 增长解耦

- 公式：Per-token FFN 使 $\#\text{Param} \times T$，而单 token FLOPs 不变
- 直觉：加参数的方式从"把矩阵乘变大"换成"把矩阵乘变多"，多个小 GEMM 可以 fuse 成一个大 kernel 并行执行
- 实际意义：1B 模型的 FLOPs/Param 比是 1.9 G/M，只有 16M 基线（6.8 G/M）的 $1/3.6$——同样算力预算能养 3.6 倍的参数

### 3.2 FLOPs 增长与实际成本解耦（高 MFU）

- 公式：$\text{MFU} = \dfrac{\text{模型实际消耗的 FLOPs}}{\text{硬件理论 FLOPs}}$
- 直觉：传统模型的碎算子在 GPU 上大部分时间都在等内存（memory-bound）；RankMixer 全是大矩阵乘，计算单元真正忙起来（compute-bound）
- 实际意义：MFU 从 4.47% 提到 44.57%（10 倍），相当于"免费"拿到 10 倍算力，再叠加 fp16 量化的 2 倍

### 3.3 无参数交互也能涨点

- Token Mixing 没有任何参数，却是最关键的组件：去掉它 AUC 掉 $-0.50\%$（所有消融项里最大）
- 直觉：它保证每个 Per-token FFN 拿到的输入都含有全局信息，"隔离参数"但不"隔离信息"
- 对比：自注意力在这个场景是"更贵且更差"的替代品

### 3.4 对低活用户提升最大

- 线上 A/B：低活用户 Active Days +1.74%，远高于高活用户的 +0.14%
- 直觉：更大的稠密容量 + 参数隔离，让长尾、低频信号不再被高频信号淹没，模型泛化能力更强

## 4. 与其他模型的关系

1. **与 Transformer 的关系**：保留"残差 + LN + Block 堆叠"的高并行骨架，替换两个核心组件——自注意力（二次复杂度、假设 token 同质）换成无参数 Token Mixing，共享 FFN 换成 Per-token FFN。
2. **与 MLP-Mixer 的关系**：名字里的 "Mixer" 一脉相承——MLP-Mixer 在 CV 里用"跨 patch 混合 + 跨通道混合"替代注意力；RankMixer 是"跨 token 混合（Token Mixing）+ token 内变换（PFFN）"在推荐上的落地，但 Token Mixing 无参数、PFFN 参数隔离，均为适配推荐异构特征的改造。
3. **与 MMoE/PLE 的关系**：MMoE 是"一份输入、多个 expert、门控加权"；RankMixer 的 Per-token FFN 是"多份输入、各自专属参数"。Sparse-MoE 版则把 PFFN 的 expert 化，配合 ReLU 路由实现 token 级动态稀疏。
4. **与 Wukong（Meta）的关系**：同属"稠密 Scaling"路线。Wukong 用 FMB+LCB 堆叠验证特征交叉的缩放律，但 FLOPs 增长比参数更快；RankMixer 在 AUC-FLOPs 曲线上明显更陡（同等算力下效果更好且更省）。
5. **与 HSTU（Meta 生成式路线）的关系**：HSTU 把推荐重构成序列生成任务；RankMixer 走判别式主干改造路线，风险更低、可直接替换现有排序模型的 Dense 部分。
6. **与后续工作的关系**：字节的 LONGER（长序列建模，序列特征作为 token 输入 RankMixer）、OneTrans（统一序列建模与特征交互的单一 Transformer）、TokenMixer-Large（解决深层梯度消失的升级版）都是这条主线的延伸；快手 UniMixer、美团 MTmixAtt 则是同一问题域的对照解法。

## 5. 具体例子

### 例子 1：手算一次 Token Mixing

**问题**：设 $T=4$ 个 token、$D=4$、$H=T=4$，看混合后新 token 长什么样。

**步骤**：记 token $\mathbf{x}_t = [x_{t,1}, x_{t,2}, x_{t,3}, x_{t,4}]$，先 SplitHead 切成 4 个 1 维 head，再把所有 token 的第 $h$ 个 head 拼成新 token $\mathbf{s}^h$。

**计算**：

- $\mathbf{s}^1 = [x_{1,1}, x_{2,1}, x_{3,1}, x_{4,1}]$（所有 token 的第 1 维）
- $\mathbf{s}^2 = [x_{1,2}, x_{2,2}, x_{3,2}, x_{4,2}]$
- 以此类推，$\mathbf{s}^3, \mathbf{s}^4$

**结果解读**：混合前 $\mathbf{x}_1$ 只含"特征组 1"的信息；混合后每个新 token 都横跨全部 4 个原 token——比如 $\mathbf{s}^1$ 同时含用户画像、视频内容、行为序列、交叉特征的第 1 个子空间片段。整个操作只是 reshape + transpose，**0 参数、0 浮点乘加**，这就是"无参数全局交互"的含义。实现上它等价于把 $(T, D)$ 张量 view 成 $(T, H, D/H)$ 后转置前两维再展平。

### 例子 2：RankMixer-100M 的参数量与 FLOPs 验证

**问题**：用论文公式验证 100M 配置（$D=768, T=16, L=2$，取 $k=4$）的参数量与 FLOPs。

**步骤**：代入 $\#\text{Param} \approx 2kLTD^2$ 和 $\text{FLOPs} \approx 4kLTD^2$。

**计算**：

- $D^2 = 768^2 = 589{,}824$
- $\#\text{Param} \approx 2 \times 4 \times 2 \times 16 \times 589{,}824 \approx 1.51 \times 10^8 \approx 151\text{M}$（量级与论文报告的 107M 一致，差异来自论文实际使用的 $k$ 略小以及 embedding 投影等细节）
- $\text{FLOPs} \approx 2 \times \#\text{Param} \approx 302\text{G}$，与论文 Table 1 的 233 G/Batch 同量级
- 对比：若用共享 FFN，参数量只有 $2kLD^2 \approx 9.4\text{M}$——Per-token FFN 把参数放大了 $T=16$ 倍，而 FLOPs/Param 比反而更低

**结果解读**：这个例子直观展示了"参数靠 $T$ 复制、计算不跟着复制"的解耦设计：想加容量就加 token 或加宽 $D$，代价是内存（存参数）而非延迟（算 FLOPs）。

### 例子 3：参数 ×70 延迟为什么不涨反降

**问题**：线上基线是 15.8M 参数的 DLRM+DCN 模型（延迟 14.5ms），换成 1.1B 的 RankMixer 后延迟是多少？

**步骤**：用延迟分解公式 $\text{Latency} = \dfrac{\#\text{Param} \times (\text{FLOPs/Param})}{\text{MFU} \times \text{Hardware FLOPs}}$，代入论文 Table 6 的四个杠杆。

**计算**（相对基线的倍数）：

- 参数量：$1.1\text{B} / 15.8\text{M} \approx 70\times$（分子变大 70 倍）
- FLOPs/Param 比：$1.9 / 6.8 \approx 1/3.6$（分子缩小 3.6 倍）
- MFU：$44.57\% / 4.47\% \approx 10\times$（分母变大 10 倍）
- fp16 量化：硬件理论 FLOPs $\times 2$（分母再变大 2 倍）
- 净效应：$\dfrac{70}{3.6 \times 10 \times 2} = \dfrac{70}{72} \approx 0.97$

**结果解读**：预测延迟约为基线的 0.97 倍——与实测完全吻合（14.3ms vs 14.5ms，还略降了）。这就是"硬件感知设计"的算账方式：**每加一分参数，就要在 FLOPs/Param、MFU、量化三本账上找回一分**。顺带一提，FLOPs 绝对值涨了 20.7 倍（107G → 2106G），但 GPU 利用率涨 10 倍 + fp16 涨 2 倍，正好把 20.7 倍消化掉。

## 6. 常见面试问题

**Q1：RankMixer 解决了推荐排序模型 Scaling 的哪两个核心障碍？**

答：一是**成本约束**——工业推荐有严格延迟和高 QPS 要求，参数不能无脑加；二是**硬件错配**——CPU 时代的手工交叉模块（DCN、DHEN 等）在 GPU 上是 memory-bound 的碎算子，MFU 只有个位数，加参数≈线性加成本，Scaling Law 的 ROI 实现不了。RankMixer 用硬件感知设计（大 GEMM、高并行）把 MFU 从 4.5% 提到 45%，实现参数 ×100 而延迟不变。

**Q2：为什么 RankMixer 不用自注意力，而用无参数的 Token Mixing？**

答：自注意力用内积算 token 相似度，前提是所有 token 共享统一语义空间（NLP 成立）；推荐的 token 来自异构特征空间（用户 ID vs 视频统计量），内积相似度没有意义，且 ID 空间可达数亿。实验上自注意力更贵还更差：替换后 AUC $-0.03\%$、参数 $+16\%$、FLOPs $+71.8\%$；而 Token Mixing 零参数零 FLOPs，消融去掉它 AUC 掉 0.50%，说明全局交互本身才是刚需，注意力不是必需品。

**Q3：Token Mixing 具体怎么操作？它和 MLP-Mixer 的 token-mixing 有什么区别？**

答：把每个 token 切成 $H$ 个 head，然后将所有 token 的第 $h$ 个 head 拼接成新 token $\mathbf{s}^h = \mathrm{Concat}(\mathbf{x}_1^h, \dots, \mathbf{x}_T^h)$，取 $H=T$ 保持 token 数不变以便残差。本质是 reshape+transpose 的确定性"洗牌"。MLP-Mixer 的 token-mixing 是一个跨 patch 的**有参数 MLP**；RankMixer 完全无参数，把建模容量的职责全部交给后面的 Per-token FFN，更符合"交互结构先验少、数据驱动为主"的推荐场景。

**Q4：Per-token FFN 和共享 FFN、MMoE expert 分别有什么区别？**

答：共享 FFN 是所有 token 用同一套参数；Per-token FFN 是每个 token 一套专属参数——**输入和参数同时切分**。MMoE 则是多个 expert 吃同一份输入、门控加权输出。Per-token FFN 的好处：参数量 ×T 而单 token 计算量不变（参数-FLOPs 解耦），且避免高频特征域淹没长尾信号。消融显示退化为共享 FFN 会掉 0.31% AUC。

**Q5：RankMixer 的参数量和 FLOPs 公式是什么？有哪些 Scaling 方向？**

答：稠密版单样本 $\#\text{Param} \approx 2kLTD^2$，$\text{FLOPs} \approx 4kLTD^2$，其中 $k$ 是 FFN 隐层放大系数、$L$ 层数、$T$ token 数、$D$ 隐藏维度。四个正交方向：加宽 $D$、加 token $T$、加层 $L$、加 expert $E$（MoE 版）。实验结论与 LLM 一致：效果主要看总参数量，各方向近似等价；但加宽 $D$ 的 GEMM shape 更大、MFU 更高，所以生产配置只有 2 层、宽度优先（1B：$D=1536, T=32, L=2$）。

**Q6：Vanilla Sparse MoE 直接用在 RankMixer 上会有什么问题？**

答：两个问题。一是**均匀 Top-k 路由不适配异构 token**：信息量大的 token 吃不饱、低信息 token 浪费 expert 预算；二是**expert 训练不足**：Per-token FFN 已把参数 ×T，再乘 expert 数会让 expert 总量爆炸，路由不均导致"死 expert"（几乎从不被激活）。实验上 Vanilla SMoE 的 AUC 随激活率降低单调下滑，加负载均衡 loss 也只能缓解，因为根子在 expert 训练而非路由器。

**Q7：RankMixer 的 ReLU 路由相比 Top-k + softmax 有什么优势？稀疏度怎么控制？**

答：ReLU 路由 $G_{i,j} = \mathrm{ReLU}(h(\mathbf{s}_i))$：(1) 天然稀疏且完全可微，没有 Top-k 的离散截断；(2) **每个 token 激活的 expert 数是动态的**，高信息 token 自动分到更多 expert，参数效率更高。稀疏度用 $\ell_1$ 正则控制：$\mathcal{L}_{\mathrm{reg}} = \sum_{i,j} G_{i,j}$，系数 $\lambda$ 把平均激活率压在预算附近，配合 $\mathcal{L} = \mathcal{L}_{\text{task}} + \lambda \mathcal{L}_{\mathrm{reg}}$ 联合训练。

**Q8：DTSI-MoE（稠密训练、稀疏推理）是怎么工作的？为什么有效？**

答：设两个路由器 $h_{\text{train}}$ 和 $h_{\text{infer}}$，稀疏正则 $\mathcal{L}_{\mathrm{reg}}$ 只加在 $h_{\text{infer}}$ 上；训练时两路都更新（训练路径接近稠密，所有 expert 都拿到充足梯度，杜绝饿死），推理只用稀疏的 $h_{\text{infer}}$ 省延迟。有效的原因：expert 训练不足的问题出在"expert 拿不到梯度"，稠密训练直接保证梯度覆盖，比事后加均衡 loss 更治本。效果是激活率 1/8 时几乎无损保留 1B 稠密 AUC，容量扩 8 倍、吞吐 +50%。

**Q9：模型参数放大 70 倍，线上延迟为什么能保持不变？请拆解。**

答：按 $\text{Latency} = \dfrac{\#\text{Param} \times \text{FLOPs/Param}}{\text{MFU} \times \text{Hardware FLOPs}}$ 四个杠杆对账：参数 ×70（分子涨），但 FLOPs/Param 从 6.8 降到 1.9（÷3.6，Per-token FFN 的参数-FLOPs 解耦），MFU 从 4.47% 升到 44.57%（÷10，大 GEMM + kernel fusion 把 memory-bound 变 compute-bound），fp16 量化（÷2）。净效应 $70 / 72 \approx 0.97$，实测延迟 14.5ms → 14.3ms。

**Q10：RankMixer 与 Wukong、HSTU 等 Scaling 工作相比，路线上有什么不同？它有什么局限？**

答：Wukong（Meta）同属稠密判别式路线，但 FMB/LCB 结构的 FLOPs 增长快于参数增长，AUC-FLOPs 曲线明显更平；HSTU 走生成式路线，把推荐重构成序列生成任务，改造成本高风险大；RankMixer 选择"只替换现有排序模型的 Dense 部分"，是收益最确定、迁移成本最低的判别式主干改造。局限：(1) Token Mixing 的固定洗牌模式不含可学习的交互先验，深层堆叠时信息传播依赖层数（后续 TokenMixer-Large 专门解决深层梯度消失问题）；(2) 序列建模仍靠外部模块（LONGER）前置编码，未与特征交互统一（后续 OneTrans 尝试统一）；(3) tokenization 依赖人工语义分组，有领域知识成本。
